# 테스트 코드 작성 규칙

각 주제는 `공통` 규칙을 먼저 적용하고, 이어서 `단위` / `슬라이스` / `통합` 중 해당 유형의 규칙을 적용한다.
한 요청에 유형이 여러 개이면 유형마다 해당 규칙을 각각 적용한다.

## 1. 테스트 유형 선택

| 유형 | 대상 | Spring 컨텍스트 |
|------|------|-----------------|
| 단위 | 순수 로직, 엔티티 등 순수 Java 객체 | 사용하지 않음 |
| 슬라이스 | 특정 레이어만 격리 (Controller, Repository 등) | 해당 레이어만 구동 |
| 통합 | 여러 기능이나 도메인에 걸친 흐름 | 모든 빈 구동 |

## 2. 테스트 코드 작성 원칙

### 프레임워크

- JUnit 5 (`org.junit.jupiter.api.*`) 및 AssertJ (`org.assertj.core.api.Assertions.*`) 기반 Fluent Assertion으로 작성
- Mocking은 Mockito (`org.mockito.*`) 활용

### Flat한 구조 유지

`@Nested` 중첩 클래스를 절대 사용하지 않으며, 단일 클래스 내 평평한 메서드 구조로 작성한다.

### 명확한 @DisplayName

테스트 의도가 한눈에 드러나도록 `@DisplayName`을 구체적이고 명확하게 작성한다.
예: `@DisplayName("성공: 재고가 충분할 때 주문 생성에 성공하고 PENDING 상태를 반환한다")`

### BDD 스타일 Given-When-Then

모든 테스트 메서드 내부는 `// given`, `// when`, `// then` 주석 블록을 명확히 구분하여 작성한다.

### 독립성 (Self-Contained)

모든 테스트는 실행 순서나 다른 테스트의 결과에 절대 의존하지 않고 독립적으로 동작해야 한다.

#### 데이터 준비

테스트에 필요한 데이터는 해당 테스트 내부, `@BeforeEach`, 또는 Fixture/Helper 메서드를 통해 직접 구성한다.

#### 상태 격리

공유 자원(DB, 파일, Static 상태 등)에 남긴 영향이 다음 테스트에 절대 영향을 주지 않아야 한다.
DB 상태 격리는 기본적으로 `@Transactional` 롤백을 활용한다.
실제 웹 환경을 띄우는 통합 테스트 등 롤백이 적용되지 않는 환경에서는 `@AfterEach`나 Cleanup 유틸리티로 명시적으로 정리한다.

## 3. 어노테이션

테스트 클래스 상단에 테스트 유형 어노테이션 중 하나를 **반드시** 붙여야 하고, **하나만** 붙여야 한다. 테스트 유형 어노테이션은 `backend/spring-core-api/src/test/java/io/github/lsgeun/ecommerce/support/annotation/`에 정의되어 있다.
테스트 클래스의 메서드에는 **절대** 테스트 유형 어노테이션를 붙이지 않는다.

필요하면 표준 Spring/JUnit 어노테이션(`@ExtendWith`, `@WebMvcTest`, `@DataJpaTest` 등)을 테스트 클래스 상단에 자유롭게 추가하여 확장한다.

## 4. Mocking

가짜 객체(Mock/Fake/Stub) 사용을 엄격히 제한하고, 가능한 한 실제 객체와 상태 기반 검증(State-based Testing)을 우선한다.

### 공통

#### 객체 대용 우선순위

의존성을 채울 때는 아래 순서를 **반드시** 준수한다.

1. **Real Object (실제 객체):** 순수 자바 객체(POJO), 도메인 엔티티, VO, DTO 등은 무조건 실제 객체를 생성하여 사용한다.
2. **Fake (가짜 구현체):** 메모리 기반 저장소(예: ConcurrentHashMap 기반의 InMemoryRepository) 등 인터페이스의 경량화된 실제 동작 구현체를 우선 검토한다.
3. **Mock / Stub (Mockito, @MockBean):** 아래 "공통 Mocking 허용 조건" 또는 유형별 규칙에 해당하는 불가피한 경우에만 제한적으로 사용한다.

#### 공통 Mocking 허용 조건

다음 두 가지 경우를 제외하고는 Mockito(`mock()`, `@Mock`, `@MockBean`, `given()`) 사용을 금지한다. (유형별 추가 허용 조건은 아래 참고)

- **외부 시스템 경계:** 외부 HTTP API Client, PG사 결제, 메일/SMS 발송 등 제어할 수 없는 외부 네트워크 통신.
- **비결정적(Non-deterministic) 요인:** `Clock`, `LocalDateTime.now()`, Random 값, UUID 생성기 등 실행 시점마다 결과가 바뀌는 요소.

#### 작성 가이드라인

- **Mockito 남발 금지:** 단순 데이터 전달용 클래스나 내부 도메인 로직에 Mockito를 사용하지 않는다.
- **협력 객체 세팅:** Entity나 VO는 Mocking하지 않고, Test Fixture 메서드(예: `createMember()`)를 만들어 실제 인스턴스를 조립한다.
- **인터페이스 중심:** 외부 API나 비결정적 요인은 인터페이스로 추상화한 뒤, 테스트 시점에만 Stubbing하거나 Fake 구현체를 주입한다.

### 유형별

- **단위:**
  - Spring 컨텍스트를 띄우지 않으므로 `@MockBean`은 애초에 사용할 수 없다.
  - 의존성은 순수 자바 객체나 Fake 구현체로 조립하는 것을 원칙으로 한다.
  - Mockito(`@Mock`, `mock()`)는 공통 허용 조건(외부 시스템 경계, 비결정적 요인)에 해당할 때만 예외적으로 사용한다.
- **슬라이스:**
  - 검증 대상 레이어(예: `@WebMvcTest`의 Controller, `@DataJpaTest`의 Repository)를 제외한 **하위 레이어와의 경계**는 `@MockBean`으로 격리하는 것을 허용한다.
    - 예: `@WebMvcTest`로 Controller를 단독 검증할 때, Service 레이어 이하는 `@MockBean`으로 대체한다.
  - 검증 대상 레이어 내부의 협력 객체(Entity, VO 등)는 공통 규칙과 동일하게 Mocking하지 않고 실제 객체로 조립한다.
- **통합:**
  - `@SpringBootTest`로 모든 빈을 실제로 구동하는 것이 목적이므로, `@MockBean`으로 내부 빈을 대체하지 않는다.
  - Mockito 사용은 공통 허용 조건(외부 시스템 경계, 비결정적 요인)으로 엄격히 제한한다.

## 5. 파일명과 디렉터리

### 유형별

- **단위:**
  - 파일명: `<검증 대상 클래스명>UnitTest.java`
  - 디렉터리: 검증 대상 클래스가 위치한 main 패키지 경로와 완전히 동일해야 한다.
    - 예: `main/.../product/application/ProductSimpleService.java` -> `test/.../product/application/ProductSimpleServiceUnitTest.java`
- **슬라이스:**
  - 파일명: `<검증 대상 클래스명>SliceTest.java`
  - 디렉터리: 단위 테스트와 동일하게 main 패키지 경로와 완전히 동일해야 한다.
- **통합:**
  - 파일명: 아래 목적 키워드 중 하나를 포함한다.
  - 목적 키워드는 아래 목록에서 선택하고, 새로운 검증 목적이 생기면 이 목록에 추가한다.
    - `Crud`: 생성/조회/수정/삭제 등 기본 기능 검증
    - `Scenario`: 여러 기능이 연계된 비즈니스 흐름 검증
    - `Query`: 복합 조회/조건 검증
    - `Concurrency`: 동시성/경쟁 상태 검증
  - **하나의 도메인에만 의존하는 경우**
    - 파일명 형식: `<도메인명>[구체적 설명]<목적 키워드>IntegrationTest.java`
    - 하나의 도메인이라도 검증 목적(키워드)이 다르면 파일을 나누어 작성한다. `<도메인명>IntegrationTest.java` 하나로 몰아넣지 않는다.
    - "구체적 설명"은 같은 키워드 안에서 파일을 구분하기 위해 자유롭게 붙인다.
    - 디렉터리: 해당 도메인 루트 패키지 바로 아래 `integration` 패키지
    - 예: `test/.../product/integration/ProductCrudIntegrationTest.java`, `ProductStockScenarioIntegrationTest.java`
  - **여러 도메인에 걸친 경우**
    - 파일명 형식: `<비즈니스 유스케이스(흐름) 이름><목적 키워드>IntegrationTest.java`
    - 관련 도메인명을 나열하지 않고, 검증 대상 비즈니스 유스케이스(흐름)의 이름을 드러낸다. 최상위 `integration/` 패키지에 위치한다는 사실 자체가 특정 도메인에 속하지 않음을 나타내므로, 도메인명 나열은 불필요한 중복이다.
    - 디렉터리: 특정 도메인에 종속시키지 않고, 최상위 test 패키지 바로 아래 `integration` 패키지
    - 예: `test/.../integration/CheckoutScenarioIntegrationTest.java`, `OrderPaymentScenarioIntegrationTest.java`

## 6. 케이스 커버리지

### 공통

- 단순 Getter/Setter, DTO 기본 생성, Spring Framework 자체의 동작은 테스트 대상에서 제외한다.
- 검증 대상 메서드 하나당 "정상 흐름 1개 이상 + 해당 메서드가 던질 수 있는 예외/실패 시나리오 전부"를 최소 기준으로 작성한다.
  - 하나의 메서드가 서로 다른 원인으로 여러 종류의 예외를 던질 수 있다면(예: 재고 상한 초과 예외와 재고 부족 예외), 원인별로 각각 케이스를 작성한다. 대표 케이스 1개로 생략하지 않는다.
- 아래 항목에 해당하는 경우가 검증 대상 메서드에 실제로 존재한다면, 빠뜨리지 않고 케이스로 작성한다. 해당 사항이 없으면 억지로 만들지 않는다.

#### 필수 검증 항목

- **부재(Not Found):** 조회/수정/삭제 대상이 존재하지 않는 경우.
- **충돌(Conflict):** 이미 존재하는 대상을 다시 생성하거나, 상태 충돌이 발생하는 경우.
- **경계값(Boundary):** 허용 범위의 최솟값/최댓값에서 정상 동작하는 성공 케이스와, 그 바로 바깥 값(최솟값-1, 최댓값+1)에서 예외가 발생하는 실패 케이스를 각각 검증한다.
- **입력값 이상(Invalid Input):** `null`, 빈 문자열, 음수 등 도메인 규칙상 허용되지 않는 입력.
- **예외 전파(Exception Propagation):** 하위 계층(도메인, 리포지토리 등)에서 발생한 예외가 상위 계층 호출부까지 그대로 전파되는지.
- **상태 변화(State change):** 성공 시 반환값뿐 아니라 대상 객체/DB의 내부 상태가 실제로 변경되었는지.

#### 성공 케이스 작성 원칙

정상 흐름은 대표값 1개로 끝내지 말고, 경계값에서도 정상 동작함을 별도 케이스로 검증한다.
예: 재고 감소는 임의의 값 1건 + 재고가 정확히 0이 되는 경계값 1건.

### 유형별

- **단위, 슬라이스:** 동시성(경쟁 상태) 검증은 대상이 아니다.
- **통합:** 동시성(경쟁 상태) 검증은 위 규칙의 대상이 아니며, 목적 키워드 `Concurrency`의 별도 통합 테스트 파일로 작성한다.

## 7. 최적화

### 유지보수 최적화 (공통)

- **상태 검증 우선:** 최종 반환값이나 객체/DB의 내부 상태 변화(`assertThat`)를 최우선으로 검증하며, 단순 메서드 호출 여부를 확인하는 `verify()` 남용을 지양한다.
- **Helper/Fixture 활용:** `given` 절이 복잡해지지 않도록 객체 생성을 전담하는 테스트 전용 Helper/Fixture 메서드를 적극 활용한다.

### 실행 최적화

#### 공통

- **최소 데이터 준비:** 해당 테스트 케이스 검증에 필요한 필드/데이터만 준비하고, 결과와 무관한 부가 데이터는 만들지 않는다.
- **느린 테스트 지양:** `Thread.sleep()` 등 실행 시간을 인위적으로 늘리는 대기 코드를 사용하지 않는다. 비동기/시간 의존 검증이 필요하면 `Awaitility` 같은 폴링 기반 도구를 사용하거나, `Clock` 추상화로 시간을 제어한다.

#### 유형별

- **단위:** 해당 없음 (Spring 컨텍스트를 사용하지 않음)
- **슬라이스, 통합:** 컨텍스트 재사용. Spring 컨텍스트가 테스트마다 불필요하게 재생성되지 않도록, 동일한 조건의 테스트는 가능한 한 같은 설정(`@ActiveProfiles`, `@MockBean` 대상 등)을 공유한다.
