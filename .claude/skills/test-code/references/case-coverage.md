# 케이스 커버리지 규칙

- 단순 Getter/Setter, DTO 기본 생성, Spring Framework 자체의 동작은 테스트 대상에서 제외한다.
- 검증 대상 메서드 하나당 "정상 흐름 1개 이상 + 해당 메서드가 던질 수 있는 예외/실패 시나리오 전부"를 최소 기준으로 작성한다.
  - 하나의 메서드가 서로 다른 원인으로 여러 종류의 예외를 던질 수 있다면(예: 재고 상한 초과 예외와 재고 부족 예외), 원인별로 각각 케이스를 작성한다. 대표 케이스 1개로 생략하지 않는다.
- 아래 항목에 해당하는 경우가 검증 대상 메서드에 실제로 존재한다면, 빠뜨리지 않고 케이스로 작성한다. 해당 사항이 없으면 억지로 만들지 않는다.

## 필수 검증 항목

- **부재(Not Found):** 조회/수정/삭제 대상이 존재하지 않는 경우.
- **충돌(Conflict):** 이미 존재하는 대상을 다시 생성하거나, 상태 충돌이 발생하는 경우.
- **경계값(Boundary):** 허용 범위의 최솟값/최댓값에서 정상 동작하는 성공 케이스와, 그 바로 바깥 값(최솟값-1, 최댓값+1)에서 예외가 발생하는 실패 케이스를 각각 검증한다.
- **입력값 이상(Invalid Input):** `null`, 빈 문자열, 음수 등 도메인 규칙상 허용되지 않는 입력.
- **예외 전파(Exception Propagation):** 하위 계층(도메인, 리포지토리 등)에서 발생한 예외가 상위 계층 호출부까지 그대로 전파되는지.
- **상태 변화(State change):** 성공 시 반환값뿐 아니라 대상 객체/DB의 내부 상태가 실제로 변경되었는지.

## 성공 케이스 작성 원칙

- 정상 흐름은 대표값 1개로 끝내지 말고, 경계값에서도 정상 동작함을 별도 케이스로 검증한다.
  - 예: 재고 감소는 임의의 값 1건 + 재고가 정확히 0이 되는 경계값 1건.

## 적용 범위 밖: 동시성

- 동시성(경쟁 상태) 검증은 이 문서의 대상이 아니다. `testcode/directory-and-filename.md`의 통합 테스트 목적 키워드 `Concurrency`에 따라 별도의 통합 테스트로 작성한다.
